# クリーンルーム5択ドリル（消化器）

医学教育モデル・コア・カリキュラムと医師国家試験出題基準に対応づけた5択問題を、ブラウザだけで解いて、自動採点と解説を受けられるサイトです。

**使ってみる**：https://hm-cmed.github.io/cleanroom-mcq/

- インストールもアカウント登録も要りません。解答の記録はブラウザの中だけに保存され、外部には送られません。
- 1問ごとに採点し、5つの選択肢すべてに「正しい記述か・誤った記述か」と、その根拠（事実カードと出典）を表示します。模擬試験のように最後にまとめて解説を見ることもできます。
- 途中でやめるときは、成績表（CSV）と再開用ファイル（JSON）を保存できます。同じブラウザなら自動で続きから再開できます。
- 結果は領域別・出題基準の項目別に集計し、間違えた問題だけを解き直せます。

## 学年に合わせた出題（おまかせ）

学年と問題数を選ぶと、配分に沿って問題を自動で選びます。

| 学年 | 選び方 |
|---|---|
| 1〜4年生 | モデル・コア・カリキュラム（令和4年度改訂版）の配分 |
| 5年生 | コアカリ半分、医師国家試験ブループリント半分 |
| 6年生・卒業生 | 医師国家試験ブループリント（令和6年版）の配分 |

学年ごとの割合は `js/config.js` の `gradeProfiles` で変えられます。

配分の目安の作り方（`tools/curriculum.py`）：

- **ブループリント**：医学各論の大項目の出題割合（設計表、例：Ⅵ 消化器は約13%）に、小項目のレベルの重み（a=3、b=2、c=1）を掛けて、大項目の下（例：Ⅵ-6 肝疾患）の目安にする。設計表には大項目の下の割合がないため、このレベルの重みは当サイトの仮定です。
- **コアカリ**：コアカリには公式の割合がないため、別表1（疾患表）と別表2（臓器別の学修項目）の項目数（基本●の疾患は2、それ以外は1）を目安にする。カードに疾患表の番号がないときは、出題基準の大項目から疾患表のカテゴリに対応づける。
- 問題が足りない区分の分は、ほかの区分に回します。今の問題の偏りと、足りない区分は「出題範囲」ページと `reports/coverage.md` で確認できます。
- ブループリントの割合と小項目の一覧は、事実票の `data/curriculum/` にあります（原本との照合が済むまでは暫定値）。

## クリーンルーム方式

問題は、教科書やガイドラインの文章を写さずに作ります。

1. 論文・ガイドラインから事実と数値だけを取り出し、自分の言葉で「事実カード」に書く（[cleanroom-facts](https://github.com/hm-cmed/cleanroom-facts)）。出典の実在とライセンスを API で照合する。
2. 問題の各選択肢に、その正誤を決める事実カードを1枚ずつ対応させる。
3. `tools/build.py` が、選択肢と事実カードを機械的に突き合わせる（カードの有無・廃止・出典照合の状態・数値の一致）。
4. 専門医が監修し、承認した問題だけを「監修済み」として公開する。

解説の文章は事実カードの主張文をそのまま使います。問題ファイルに解説を手で書かないので、カードを直せば解説も直ります。医師国家試験の過去問題は使いません。

## フォルダ

| 場所 | 中身 |
|---|---|
| `index.html` `js/app.js` `css/style.css` | サイト本体（ビルド不要の静的ファイル） |
| `js/config.js` | 表示の設定（名前、開発者、監修前の問題を出すか、助成の表記） |
| `items/*.yaml` | 問題の原本（人が編集する） |
| `tools/build.py` | 問題を事実票と照合し、`data/questions.js` を作る |
| `data/questions.js` | サイトが読む問題データ（自動で作る。直接編集しない） |
| `reports/check_report.md` | 照合の結果（エラーと、監修のときに見る注意点） |
| `reports/coverage.md` | ブループリント・コアカリの配分の目安と、今の問題数・使えるカード数 |
| `tools/curriculum.py` | 学年別の配分に使う分類と目安の計算 |
| `review/` | GitHub で監修するためのページ（自動で作る） |
| `.github/` | 監修フォームと、自動更新・公開の仕組み（GitHub Actions） |

## 問題の書き方

```yaml
- id: Q-LV-001            # Q-<領域>-<3桁>。一度付けたIDは使い回さない
  ask: true               # true＝「正しいのはどれか」、false＝「誤っているのはどれか」
  stem: 肝硬変の腹水について正しいのはどれか。
  options:                # 必ず5つ。正答は ask と truth が一致する1つだけ
    - {text: （選択肢の文）, truth: true,  fact: LV-006}
    - {text: （選択肢の文）, truth: false, fact: LV-010}
    # …
  status: draft           # draft（監修前）/ approved（監修済み）/ retired（廃止）
  # approved・reviewer・reviewed_at・reviewed_hash は、GitHub の監修フォームから自動で書かれる
```

- `fact` には、その選択肢が正しい・誤っていると言える根拠のカードIDを書きます。
- 正しい選択肢に入れる数字は、カードの主張文にある数字と一致させます（違うとビルドが止まります）。
- 誤りの選択肢で数字を変えた場合は「注意」として報告されます。意図したものか監修で確認してください。
- 正答の根拠になるカードは、出典の照合が済んだもの（`verified_sources` 以上）に限ります。

## 問題データを作り直す

事実票のレポジトリを隣に置いて実行します（Windows の PowerShell）。

```powershell
git clone https://github.com/hm-cmed/cleanroom-facts ..\cleanroom-facts
pip install pyyaml
python tools\build.py
```

エラーが0件なら `data/questions.js` が更新されます。

## 監修の進め方（GitHub で行う）

監修は GitHub の画面だけでできます。プログラムの知識は要りません。

1. 監修者に GitHub のアカウントを作ってもらい、このレポジトリの Settings → Collaborators で招待する（書き込み権限のある人の監修だけが自動で反映されます）。
2. 監修者は [review/README.md](review/README.md) を開き、領域のページで問題・正答・各選択肢の根拠カードを確認する。
3. 問題がなければ「まとめて承認する」、直すべき問題は「この問題を監修する」→「修正が必要」から送信する（Issue フォームが開き、問題IDと版は自動で入る）。
4. 数分で GitHub Actions が `items/*.yaml` に監修者・日付・版を記録し、サイトでも「監修済み」として出題されます。修正案は `proposals/` に残り、問題は書き換えません。
5. 監修したあとに問題文や根拠カードの内容が変わると、その問題は自動で「監修前」に戻り、監修ページに「再監修が必要」と表示されます。
6. 監修済みの問題がそろったら、`js/config.js` の `showDrafts` を `false` にすると、監修前の問題は出題されなくなります。

利用者は「問題の誤りを知らせる」フォーム（Issues → New issue）から、誤りを報告できます。

## 事実票との自動連携

問題の解説は事実カードの最新の文章から作ります。事実カードが監修・修正されると、次のどれかのときに問題サイトも自動で最新版になります。

- 毎日 4:00（日本時間）の自動更新
- 事実票側で監修が反映されたときの通知（下の 2. を設定した場合）
- Actions タブの「問題データの更新」→「Run workflow」

### 最初に1回だけ行う設定

1. **サイトの公開**：このレポジトリの Settings → Pages → Build and deployment の Source を「GitHub Actions」にする。
2. **事実票を読むためのトークン**（事実票が非公開レポジトリの間は必要）：
   1. GitHub 右上のアイコン → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token。
   2. Repository access で `cleanroom-facts` と `cleanroom-mcq` を選び、Permissions の Contents を「Read and write」にして作成する。
   3. できたトークンを、`cleanroom-mcq` の Settings → Secrets and variables → Actions に `FACTS_REPO_TOKEN` という名前で登録する。
   4. 同じトークンを、`cleanroom-facts` の同じ場所に `MCQ_DISPATCH_TOKEN` という名前で登録する（事実票の監修が反映されたとき、すぐに問題サイトへ知らせるため。登録しなくても毎日の自動更新で反映されます）。
   5. トークンには有効期限があります。期限が切れたら作り直して登録し直してください。

事実票を公開レポジトリにした場合は、2. の `FACTS_REPO_TOKEN` は不要です。
